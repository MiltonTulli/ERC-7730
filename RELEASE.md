# Releases — @erc7730/sdk

This repo publishes **one** public package: [`@erc7730/sdk`](https://www.npmjs.com/package/@erc7730/sdk).

Never publish `@erc7730/registry` or `@erc7730/web`. Both are ignored by Changesets. The registry is a workspace build input (the SDK embed is generated by `packages/sdk/scripts/build.js`); the web package is the GitHub Pages demo.

Versioning is **human + Changesets**. Publishing is the **git tag** workflow `.github/workflows/release.yml`. There is no publish-on-push-to-main.

## Semver while on 0.x

| Bump | When |
| --- | --- |
| `0.2.x` | Official registry client, ERC-7730 v2 types/schema (see [ROADMAP.md](./ROADMAP.md)) |
| `0.3.x` | Breaking decode API (`decodeTransaction` / `decodeTypedData`, `ClearSigner` deprecation) |
| `0.4.x` | CLI + adapters |
| `0.5.x` | Multicall / UserOp / attestations |
| **patch** (`0.x.Y`) | Bugfix, docs in the published tarball, no public API break |

Do not jump to `1.0.0` from this runbook.

Do not use the npm `latest` tag for experiments. A future `--tag canary` pipeline is out of scope here.

## Add a changeset in a feature PR

When you change `packages/sdk/src/**` or `packages/sdk/package.json`, CI requires a file under `.changeset/` other than `README.md`.

```bash
pnpm changeset
```

Pick `@erc7730/sdk`, the bump type (`patch` / `minor` / `major` — on 0.x, `minor` is the usual feature bump), and a short summary. Commit the generated `.changeset/<id>.md` with the feature.

Docs-only, workflow-only, web-only, and registry-descriptor PRs do **not** need a changeset.

## Cut a release

1. Merge feature PRs (with changesets) to `main`.
2. From a clean `main`:

```bash
pnpm version-packages   # or: pnpm changeset version
# review CHANGELOG.md and packages/sdk/package.json
git add .
git commit -m "chore: version packages"
git push origin main
VERSION=$(node -p "require('./packages/sdk/package.json').version")
git tag "v$VERSION"
git push origin "v$VERSION"
```

3. Pushing `vX.Y.Z` runs [`.github/workflows/release.yml`](./.github/workflows/release.yml).
4. If GitHub Environment `npm` has a required reviewer, **approve the deployment** or the job stays waiting.

Do not run `npm publish` or `pnpm release` from a laptop unless recovering from a broken tag workflow.

## What the tag workflow does

On `push` of tags matching `v[0-9]+.[0-9]+.[0-9]+` (e.g. `v0.1.4`, not `vnext`):

1. `pnpm install --frozen-lockfile`
2. `pnpm build` / `typecheck` / `test`
3. **Version guard:** tag `v0.1.3` must equal `packages/sdk/package.json` `"version": "0.1.3"`. Mismatch fails the job.
4. `npm pack` in `packages/sdk`. Fails if the tarball contains `src/`, tests, or `.map` files.
5. `npm publish <tarball> --access public --provenance` via **OIDC Trusted Publishing** (no `NPM_TOKEN`).
6. Creates a GitHub Release for that tag and attaches the same `.tgz`.

Only `@erc7730/sdk` is published. The job uses `environment: npm`.

The first tag publish **will fail** until Trusted Publishing and the GitHub Environment exist. That is expected. Do not push a production tag before those two clicks.

## Maintainer setup (one-time)

### 1. GitHub Environment `npm`

1. Repo **Settings → Environments → New environment**
2. Name: `npm` (must match the workflow `environment:` value exactly)
3. Add a **required reviewer** (yourself, or a release owner)
4. Optional: restrict to tags / selected branches. The workflow only runs on `vX.Y.Z` tags.

The workflow file can reference `environment: npm` before the Environment exists. GitHub may auto-create an unprotected one on first run; add the reviewer before you cut a real release.

### 2. npm Trusted Publishing (OIDC)

Requires npm CLI **≥ 11.5.1** on the runner (the release workflow installs `npm@11`). GitHub-hosted runners only.

1. Open [npmjs.com/package/@erc7730/sdk](https://www.npmjs.com/package/@erc7730/sdk) while logged in as a maintainer of the `@erc7730` scope
2. **Package settings** (or **Access**) → **Trusted Publisher**
3. Publisher type: **GitHub Actions**
4. Fill in:
   - **Organization or user:** `MiltonTulli`
   - **Repository:** `ERC-7730`
   - **Workflow filename:** `release.yml` (filename only, not `.github/workflows/release.yml`)
   - **Environment name:** `npm`
5. Save. If the UI asks which actions to allow, permit **`npm publish`** (not only staged publish).

Do **not** add `NODE_AUTH_TOKEN` / `NPM_TOKEN` to the release workflow. `setup-node`'s `registry-url` writes a dummy `_authToken`; the workflow strips it so the npm CLI can do the OIDC exchange.

`--provenance` is required and needs `permissions.id-token: write` on GitHub-hosted runners.

### 3. Branch protection

Protect `main` and require the `CI` workflow (lint + Node 20/22 build/test). Pages and Release are separate.

## Rollback

npm **cannot unpublish** a version after 72 hours, or if anyone else has installed it. Do not unpublish.

```bash
npm deprecate @erc7730/sdk@X.Y.Z "Broken; use @erc7730/sdk@A.B.C"
```

Then publish a patched version via the tag workflow.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `ENEEDAUTH` / `E404` on publish | Trusted Publisher not configured, or `_authToken` still in `.npmrc` (OIDC never starts) |
| Job waiting on Environment | Approve the `npm` environment deployment |
| Version guard failed | Tag `vX.Y.Z` does not match `packages/sdk/package.json` |
| Tarball inspect failed | `files` in `packages/sdk/package.json` leaked `src/`, tests, or sourcemaps |
| Pages did not deploy | Path filter: README-only pushes no longer trigger Pages |
